Данные сервисов и файлы конфигурации распределяются по четырём [уровням](/apex/glossary#tier) хранилища. Статическая декларативная конфигурация и зашифрованные секреты хранятся непосредственно в репозитории узла на **Уровне 0**, а персистентное состояние приложений, базы данных и журналы распределяются по трём внешним уровням хранилища (**Уровень 1** — **Уровень 3**) и подключаются к [композициям](/apex/glossary#compositions) через стандартизированную структуру символьных ссылок. Права на эти каталоги делегируются системным пользователям проектов, благодаря чему ни один контейнер не ведёт запись от имени root.

## Уровень 0 (`@tier0`) — конфигурация и секреты в репозитории {#tier0}

В отличие от внешних уровней `@tier1`–`@tier3`, каталог `compositions/<project>/@tier0/` располагается непосредственно внутри репозитория узла и отслеживается в Git:

- **Открытые файлы конфигурации** (динамические маршруты Traefik, конфигурации Nginx, правила маршрутизации и необходимые шаблоны), не содержащие секретов, коммитятся в `compositions/<project>/@tier0/` напрямую.
- **Конфигурационные файлы с секретами** (например, `AdGuardHome.yaml`, `config.jsonc` для Xray, `rclone.conf`, `app/config.ini`, `service/settings.yml` или статические закрытые ключи TLS) хранятся в Git в зашифрованном виде SOPS как `<имя>.enc.<расширение>` (или `<имя>.enc` для файлов без расширения). На хосте они расшифровываются в рабочие пути, которые автоматически перечисляются в `compositions/<project>/@tier0/.gitignore`.

Для уровня `@tier0` действуют три жёстких ограничения, проверяемых линтером `util/lint-docker-compose` (включая pre-commit хук) и действием `repository/sync`:

1. **Лимит размера 256 КБ:** размер любого файла в `@tier0` не должен превышать 256 КБ (`262 144` байта).
2. **Никакого часто изменяемого состояния:** базы данных и журналы WAL (`*.db`, `*.db-shm`, `*.db-wal`, `*.sqlite*`, `*.mv.db`), кэши сертификатов ACME (`acme.json`), журналы DNS-запросов (`querylog*.json*`), логи, lock/pid/socket-файлы и резервные копии (`*.log`, `*.pid`, `*.lock`, `*.sock`, `*.bak*`, `*.torrent`) размещаются на уровне `@tier1` или выше.
3. **Приоритет структурированных форматов SOPS:** для файлов `dotenv`, `yaml`, `json` (включая валидный JSON в `.jsonc`) и `ini` используется поключевое шифрование SOPS, сохраняющее читаемость git-diff. Режим `raw` применяется только к неструктурированным текстовым форматам и статическим ключам.

## Структура ссылок уровней {#links}

Команда `apex tier/link <tier1> <tier2> <tier3>` формирует структуру символьных ссылок:

- **Уровень 0:** создаёт `compositions/@tier0` и проектные каталоги `compositions/<project>/@tier0`, связывая `compositions/@tier0/<project>` → `../<project>/@tier0`.
- **На уровне узла (внешние уровни):** `compositions/@tierN` → корень хранилища соответствующего уровня (`APEX_TIER_ROOT1..3`).
- **Для каждого проекта (внешние уровни):** в каталоге `compositions/<project>/` создаётся путь `<tier-root>/<project>/`, на который указывает ссылка `compositions/<project>/@tierN`. Внутри каждого уровня поддерживается общий каталог `shared/` с поддиректорией для каждого проекта, а внутри каталога уровня проекта создаётся относительная ссылка `shared`, ведущая обратно в общую зону.

Каждый проект дополнительно содержит файл секретов `compositions/<project>/.env` (права `0600`), парный к зашифрованному файлу `compositions/<project>/.enc.env` (см. [Концепция: Композиции и общее ядро](/apex/concepts/compositions)). Ссылки `@tier1..3` и открытые файлы `.env` исключены из git через `.gitignore`, благодаря чему репозиторий остаётся чистым источником кода.

Если по пути предполагаемой символьной ссылки уже существует обычный файл или каталог, действие предупреждает об этом и запрашивает подтверждение перед удалением. При отказе (включая неинтерактивный EOF) создание ссылки пропускается, а выполнение продолжается дальше.

## Пользователи и группы {#users}

Команда `apex tier/useradd` создаёт по одному заблокированному системному пользователю на проект — `noroot-<project>` (с санитизацией имени и собственной первичной группой), а также общефлотовую группу `noroot-shared`, в которую входят все пользователи проектов. Затем сгенерированные идентификаторы прописываются в файл `.env` соответствующего проекта между комментариями-маркерами, перезаписывая старый блок при повторных запусках:

```ini {filename="compositions/<project>/.env"}
# START AUTO GENERATED APEX-NOROOT-USERS
APEX_UID=998
APEX_GID=998
APEX_SHARED_GID=997
# END AUTO GENERATED APEX-NOROOT-USERS
```

Композиции подключают эти идентификаторы через переменные `user: "${APEX_UID?error}:${APEX_GID?error}"` и `group_add: ["${APEX_SHARED_GID?error}"]`.

Если сервис в композиции обязан запускаться от `root` и отказывается работать с каталогами, принадлежащими не-root пользователю, в корне проекта размещается файл-маркер `compositions/<project>/.apex-root-owned`. При его наличии `tier/useradd` пропускает создание `noroot-<project>`, а `tier/chown` рекурсивно выставляет `root:root` на внешних уровнях и `adam:root` на `@tier0`.

## Матрица владения {#ownership}

Действие `apex tier/chown` выставляет корректные права по всем четырём уровням хранилища. Без аргументов оно обрабатывает корни уровней (`APEX_TIER_ROOT0..3`); при необходимости можно указать конкретные пути вручную.

| Путь | Владение | Примечания |
|---|---|---|
| `compositions/@tier0` | `adam:adam` | Только inode каталога (`0770`). |
| `compositions/<project>/@tier0` | `adam:gid` | Рекурсивно (`u+rwX,g+rwX,o-rwx`); `adam:root` при наличии `.apex-root-owned`. |
| `<tier-root>` | `root:root` | Только inode каталога. |
| `<tier-root>/shared` | `root:root` | Только inode каталога (без рекурсии, чтобы не затронуть пользовательские данные проектов). |
| `<tier-root>/node-infra` | `root:root` | Рекурсивно. |
| `<tier-root>/<project>` | `uid:gid` | Рекурсивно; идентификаторы читаются из `.env` проекта. |
| `<tier-root>/shared/<project>` | `uid:shared_gid` | Рекурсивно, с установкой sticky-бита: участники могут добавлять файлы, но удалять — только собственные. |

Проекты с неполным набором переменных `APEX_UID`, `APEX_GID` или `APEX_SHARED_GID` пропускаются с предупреждением и рекомендацией выполнить `tier/useradd`.

## Переменные уровней движка {#variables}

| Переменная | Разрешается в |
|---|---|
| `APEX_TIER_ROOT0` | Корень репозиторного уровня `@tier0` (`compositions/@tier0`). |
| `APEX_TIER0` | Каталог уровня `@tier0` ядрового проекта (`compositions/apex/@tier0`). |
| `APEX_TIER_ROOT1..3` | Корни внешних хранилищ уровней (`compositions/@tierN`, абсолютные пути). |
| `APEX_TIER1..3` | Каталоги данных ядрового проекта на каждом уровне (`compositions/apex/@tierN`). |
| `APEX_TIER1..3_SHARED` | Общие области внутри уровней ядрового проекта. |

Ядровая композиция монтирует каталоги исключительно через эти переменные. Контейнер резервного копирования, напротив, монтирует общий корень данных флота `/srv` в режиме «только для чтения» и сопоставляет контейнерные пути каждого сервиса с их реальными путями на хосте.

## Резервное копирование {#backups}

Команда `apex backup/run <telegram-bot-url>` полностью берёт на себя управление сервисом `resticontainer` (профиль `manual`, одноразовый запуск). Резервное копирование **управляется метками**: resticontainer находит все контейнеры с меткой `restic.enable=true`, считывает список путей `restic.backup.paths` (и необязательные параметры `restic.backup.stop` / `restic.hooks.*`), транслирует пути контейнеров в пути хоста и создаёт единый снимок restic.

1. Проверяет доступность репозитория с помощью команды `snapshots`; при необходимости автоматически инициализирует его.
2. Запускает команду `backup` с параметрами `--host <APEX_NODE_HOST>` и `--tag biweekly`. При этом resticontainer выполняет pre-hook сервиса, временно останавливает контейнеры с меткой `restic.backup.stop`, делает снимок хостовых путей, перезапускает остановленные контейнеры и запускает post-hooks. Запуск не засчитывается как успешный, если в репозитории не появился новый снимок (защита от ложного успеха при отсутствии помеченных сервисов).
3. Применяет политику хранения с помощью `forget --prune` (хранятся 7 ежедневных, 4 еженедельных и 12 ежемесячных снимков).
4. Отправляет статус выполнения в Telegram. Если уведомление не удалось доставить, операция завершается с кодом ошибки `1` даже при успешном бэкапе, чтобы сбой в канале оповещения не остался незамеченным.

Параметры подключения и учётные данные репозитория считываются из конфигурации `APEX_RESTIC_*` (см. [Справочник: Переменные окружения](/apex/reference/environment)). Состав сохраняемых данных определяется метками каждого отдельного сервиса. Например, для ядровых сервисов копируются только файлы конфигурации (динамические правила traefik, настройки xray и adguard), тогда как легко восстановимые данные уровня 3 (кэши и журналы) в снимок не включаются.
